# 05. 4 Drop Item

> 머지판과 연동되는 수집형 라이브 이벤트 — 블록 소환 · 도감 완성 · 무한 모드

**이 컨텐츠는 git 이력상 전 파일이 단일 작성자 커밋으로만 구성되어 있어, 기여가 가장 명확합니다.**

---

## 컨텐츠 개요

머지 게임 본편의 **머지판(보드)** 위에서 진행되는 이벤트입니다.
화단을 탭하면 재화를 소모해 블록이 머지판으로 소환되고, 그 블록을 머지해 도감을 채웁니다.

```
[화단 탭] ──재화 소모──> 블록 소환 (활성 화단 수만큼 동시 소환)
                              │
                        머지판에서 머지 → 상위 블록
                              │
                   ┌──────────┴──────────┐
                   ▼                     ▼
             도감 채우기            영역 해금 (열쇠)
                   │                     │
             도감 완성 연출        열쇠 비행 연출
                   │
             무한 모드 (반복 보상 + 순위)
```

컨텐츠 내부 명칭은 테마 아트 기준으로 붙어 있습니다 —
**바구니 = 활성화 블록**, **도시락 = 방출 블록**, **화단 = 성장 블록**, **물뿌리개 = 재화 HUD**.

/// 공용 헬퍼(MergeEventHelper)를 건드리지 않으려고 분리한 파일이라 FourDropItem 외 경로에서는 호출되지 않는다(additive).

기존 규약은 **재사용하되 수정하지 않는** 방식을 택했습니다.

## 기술적으로 볼 만한 부분

### 1. 모순된 기획서를 코드로 흡수하기

기획서가 같은 수치를 두 절에서 다르게 적어둔 상태였습니다.
상수를 박는 대신 **판정 축 자체를 바꿔** 수치 변경에 영향받지 않게 만들었습니다.

```csharp
/// 단계 수치를 상수로 박지 않는 이유: 기획서가 "N단계"의 N을 두 절에서 서로 다르게 적어 모순 상태다.
/// 그래서 "더 이상 업그레이드가 없는 최종 단계인가"로만 판정한다(수치가 바뀌어도 CSV 행 수만 바뀐다).
/// 최종 단계 규약은 CSV 실측으로 확인했다 — MergeEvent_Block_Main.csv 의 upBlockIdx 는 자기참조가 아니라
/// '없음 = 0' 규약이고(dangling 참조 0건), 그룹 내 최고 blockLevel 행이 0을 갖는다(머지 불가 생성기 그룹은 전 행이 0).
/// 이 규약을 이미 코드로 표현한 것이 FsEventBlockData.IsMaxLevel() 이라 그대로 재사용한다.
```

세 단계를 거친 판단입니다.

1. 기획서가 모순이니 **수치를 신뢰하지 않는다**
2. CSV **전수 실측**으로 실제 규약을 확인한다 (dangling 참조 0건까지 검증)
3. 그 규약을 **이미 표현한 기존 코드를 재사용**한다 (`IsMaxLevel()`)

기획 수치가 또 바뀌어도 코드는 그대로입니다.

### 2. 두 번 뒤집힌 스펙의 추적

`cycleChk` 플래그는 의미가 두 번 반전된 값입니다. 원시값 비교를 금지하고 상수를 경유하게 강제했습니다.

```csharp
//MergeEvent_FourDropItemCycle.cycleChk 규약(기획서 정정본).
//  1 = 주기 사용     → 레어가 나오면 그 자리에서 리셋. 안 나오면 rareCycle 회차에서 리셋
//  0 = 주기 사용 안함 → 레어가 나와도 주기 횟수를 다 채운 뒤 리셋(rareCycle 을 안 보므로 확률표 길이가 곧 주기다)
// 의미가 두 번 뒤집힌 값이다(v16 은 0=사용/1=사용 안함, v17 이 라벨을 지금처럼 되돌렸다).
//  원시값을 그대로 비교하지 말고 반드시 이 상수를 경유한다.
public const int CYCLE_CHK_USE = 1;
public const int CYCLE_CHK_UNUSE = 0;
```

더 중요한 건 **어떻게 결론을 냈는지**가 남아 있다는 점입니다.
기획서 본문(불릿)과 예시 문단이 정반대였고, 한때 불릿을 정본으로 채택했다가
이슈 코멘트의 실측 요구("최대 6번째에서 블록이 등장해야 함")로 **반증**된 뒤 예시 문단이 정본이 됐습니다.

```
옛 해석(주기를 다 채움)에서는 주기 경계가 고정이라
간격이 (rareCycle - 이전위치) + 다음위치 가 되어 최대 8탭까지 벌어졌다(7탭이 21.8%).
```

**확률 분포를 직접 계산해 가설을 반증**한 과정이 주석에 남아 있습니다.

### 3. 정수 만분율

```csharp
//rateArr 은 만분율이다(기획서 "각 등장 확률 관리(만분율, 최대 10개)").

```

(당근뽑기의 `EventCarrotSpawnSelector` 도 같은 방침입니다.)

### 4. UI 구조 변경의 이유를 남기기

화단 드랍 버튼이 패널 1개에서 칸별 4개로 쪼개졌는데, 그 이유가 명시돼 있습니다.

```csharp
/// [UI 변경] 드랍 버튼이 FieldPanel 하나에서 화단 칸마다(Field01~04)로 쪼개졌다.
///   프리팹에서 FieldPanel 자신의 UIButtonEx·Image 는 꺼졌고(m_Enabled: 0),
///   대신 각 칸이 자기 버튼을 갖는다. 칸을 나눈 이유는 재화가 모자랄 때 안내 말풍선을
///   눌린 칸 바로 위에 띄워야 하기 때문이다(기획서 "아이템 생성 영역"의 아이콘 안내).
///   네 칸의 소환 동작 자체는 완전히 같다 — 어느 칸을 눌러도 활성 화단 수만큼 나온다.
```

프리팹의 컴포넌트가 꺼져 있는 이유까지 코드에 적어두었습니다.
**프리팹 인스펙터 상태는 코드만 봐서는 알 수 없는 정보**라, 이런 주석이 없으면
다음 사람이 "왜 버튼이 안 먹지?"로 시간을 씁니다.

### 5. 이벤트 이름과 데이터 상한의 일치

```csharp
/// 활성 화단 수가 곧 1회 소환 수다 — MergeEvent_FourDropItemCycle 의 itemDropCount(1~4)와 같은 축이고
/// MergeEventHelper.GROW_MAX_COUNT(4)가 상한이라 이벤트 이름의 '4 Drop' 과도 일치한다.
/// 최소 1개는 항상 활성이다(MIN_ACTIVE_FIELD_COUNT) — 0이면 탭해도 아무 일이 없는 (상태가 된다)
```

테이블 컬럼 상한, 공용 상수, 이벤트 이름이 모두 4로 맞물린다는 것을 확인하고 기록했습니다.
그리고 **하한 방어**(최소 1개)를 두어 "탭해도 아무 일이 없는" 상태를 구조적으로 차단했습니다.
